# Demo 1: Fine-tune a small LLM with LoRA

**Use case:** turn a free-text message about a medicine into a structured safety record.

```
"After taking ibuprofen I had chest pain and was admitted to hospital."
        ↓  fine-tuned model
{"is_adverse_event": true, "drug": "ibuprofen", "reaction": "chest pain", "serious": true}
```

In pharma this step is called **adverse event (AE) intake**: a pharmacovigilance team has to spot
every message that describes a side effect, record it in a fixed format, and flag the serious ones
fast. It is a good first fine-tuning task because the output format is strict and easy to score.

> All data here is **synthetic** (generated by `make_dataset.py`). No real patients or reports.
> This is a learning demo, not a validated pharmacovigilance system.

## What you will learn

| Step | File | Idea |
|---|---|---|
| 1. Make data | `make_dataset.py` | Training data is pairs of *input* and *correct output*. A held-out test set with **unseen drug names and sentence styles** shows if the model learned the skill. |
| 2. Fine-tune | `train_lora.py` | **LoRA**: freeze the base model, train small add-on matrices (about 1% of the weights). Loss is only counted on the answer part. |
| 3. Evaluate | `evaluate.py` | Run the same test **before and after**. Score valid JSON, AE detection, drug name, seriousness, and all fields exact. |
| Shared | `common.py` | The prompt (with the model's chat template), JSON parsing and scoring. |

## How to run it

You need Python 3.10+ and about 4 GB of free RAM. A GPU is optional.

```bash
cd ai-demos/01-finetuning-lora
python -m venv .venv
.venv\Scripts\activate          # Windows   (macOS/Linux: source .venv/bin/activate)
pip install -r requirements.txt

python make_dataset.py           # 300 train + 60 test examples in data/
python evaluate.py               # BEFORE score of the base model (optional, to see the starting point)
python train_lora.py             # fine-tune; saves outputs/lora-adapter/
python evaluate.py --adapter outputs/lora-adapter   # before vs after table
```

The table is saved to `results/eval_report.md`. Each test answer is in
`results/predictions.jsonl`, so you can read where the model is still wrong.

The default model is `Qwen/Qwen2.5-0.5B-Instruct` (about 1 GB, downloaded once from Hugging Face).
To try another one, add `--model <name>` to both `train_lora.py` and `evaluate.py`,
for example `--model HuggingFaceTB/SmolLM2-360M-Instruct` (smaller, faster).

| Hardware | Training (300 examples, 2 epochs) |

## What to expect

The base model usually answers in sentences, wraps JSON in extra text, or guesses the keys. After
LoRA it should return clean JSON almost every time and get most fields right on drugs it never saw.
The exact numbers depend on the model and hardware, so run it and put **your** table in your
portfolio. The most interesting rows to talk about are the ones it still gets wrong.

**Tested here:** the whole pipeline (data, training loop, saving, loading the adapter, scoring) was
run end to end with a tiny test model on a CPU-only machine without internet access to Hugging
Face. It went from 0% to 92% valid JSON. The real Qwen numbers come from your own run.

## Key words, in plain language

- **Base model:** a model that was pre-trained by someone else on lots of text.
- **Fine-tuning:** more training on your own examples so it does *your* task, in *your* format.
- **LoRA (Low-Rank Adaptation):** fine-tuning by training small extra matrices instead of the whole
  model. `--lora-r` sets their size.
- **Epoch:** one pass over all training examples.
- **Loss:** how wrong the model is on the training answers. It should go down while training.
- **Learning rate (`--lr`):** how big each update step is. Too high and training is unstable.
- **Held-out test set:** examples kept away from training, to check the model generalises.
- **Adapter:** the saved LoRA weights (a few MB). You load it on top of the same base model.

## When to fine-tune, and when not to

Try a good prompt first, then RAG (giving the model documents at question time). Fine-tune when you
need a **fixed output format**, a **specific style**, or a **small, cheap model** that does one
narrow task well. In pharma, a fine-tuned model that feeds a regulated process (like real AE
intake) has to be validated, versioned and monitored like any other computerized system. See
[../PHARMA-COMPLIANCE.md](../PHARMA-COMPLIANCE.md).

## Ideas to extend it

- Add a field (for example `"patient_age"`) and update the generator and scoring.
- Make the data harder: spelling mistakes, two drugs in one message, Hindi or Urdu text.
- Compare LoRA ranks 4, 8 and 16, and plot score against training time.
- Try QLoRA (4-bit base model) on Colab to fine-tune a 3B or 7B model.
